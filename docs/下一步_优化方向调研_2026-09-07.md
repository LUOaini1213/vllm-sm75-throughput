## 0. 先说这轮调研改写了什么（都已按源码核实）

### 0.1 SGLang 台阶的根因措辞要改：不是「显存卡死」，是「档位表」

`results_t4/dip_rootcause_2026-09-05.txt` 与 README D 段写的是「捕获范围被显存卡死：avail mem=1.91 GB」。
SGLang v0.5.19 源码 `python/sglang/srt/arg_groups/memory_hook.py` 按 **GPU 总显存**分档，原文：

```python
if gpu_mem < 20 * 1024:
    # T4, 4080
    # (chunked_prefill_size 2k, max_bs 8)
    ...
    if decode_cuda_graph_config.max_bs is None:
        decode_cuda_graph_config.max_bs = 8
elif gpu_mem < 35 * 1024:
    # A10, 4090, 5090   → max_bs 24
elif gpu_mem < 60 * 1024:
    # A100 (40GB), L40  → max_bs 32
elif gpu_mem < 90 * 1024:
    # H100, A100        → max_bs 256
```

该文件没有任何「按运行时可用显存下调 max_bs」的逻辑。`avail mem=1.91 GB` 只是捕获前的快照，不是原因。
候选桶表在 `cuda_graph_hook.py::generate_decode_cuda_graph_batch_sizes`：
`[1, 2, 4, 8, 12] + range(16, 257, 8) + ...`，再按 `bs <= max_bs` 过滤，所以 T4 上得到 `[1, 2, 4, 8]`。

因此本轮因果 notebook 已改成单变量：C 组只加 `--cuda-graph-max-bs-decode 32`，不再动 `--mem-fraction-static`。

### 0.2 「T4 无 Marlin」是错的前提

`results_t4/quant_fp16_awq_gptq_2026-09-05.txt`、`roofline_decode_2026-09-05.txt`、README B 段、
`00_说明与索引/事实锁定.md` 第 49 行、`07_经历素材/项目经历_简历可贴.md` 第 271 行都写了「前提（sm_75 无 Marlin）对，推论错」。

- vLLM PR #29901「add marlin kernel support for turing (sm75)」**2025-12-16 已合并**，明确列出 T4；
  Turing 上无 cp.async 改同步加载、m16n8k8 双发模拟 m16n8k16、用 FP16 累加器。
- v0.28.0 `marlin_utils.py::query_marlin_supported_quant_types`：`if device_capability < 75: return []`。

所以在 vLLM 0.28.0 上，T4 的 AWQ / GPTQ-Int4 **很可能已经走了 Marlin**。那轮「预测错」的原因要改写：
不只是推论错，前提本身就错了。是否真的走了 Marlin，以 `cloud_cross_vllm_graph.ipynb` 第 7 节抓的启动日志为准，不猜。

### 0.3 已有 vLLM 数据的基线口径，README 要补两句

- vLLM 0.28 默认 `max_num_batched_tokens` 已从 8192 提到 **16384**（PR #51726，2026-08-11 合并）。
- async scheduling 自 PR #27614（2025-12-29）起**默认开启**。

我们所有 vLLM 曲线都是在这两个默认下测的，之前没写明。

### 0.4 三轮重复测量的一个口径隐患

vLLM 官方压测文档明确警告：对同一服务器重复跑会复用残留前缀缓存而虚高吞吐。
我们的 `sglang_outliers_repeat` 三轮**打的是同一个服务实例**（当时是为了隔离启动差异）。
这条要写进那份文件的边界里；重测时每轮重启或 `--flush-cache`。

## 2. 立刻做 / 值得做 的具体做法

### A. CUDA graph 因果实证（本轮正在跑）

- SGLang 三组：默认 / `--cuda-graph-backend-decode disabled` / `--cuda-graph-max-bs-decode 32`，其余参数全同。
- vLLM 三组：默认 / `--enforce-eager` / `--compilation-config '{"cudagraph_capture_sizes": [1, 2, 4, 8]}'`。
- 跑前预测：B 组台阶消失且 batch 4/8 也慢；C 组台阶右移到 32 之后；vLLM 砍桶后在 8→12 出现同样台阶。
- 任一不成立，README D 段照改。

### B. W8A8 INT8

- 为什么：INT4 weight-only 只省访存，并发 ≥16 后优势从 1.9× 缩到 1.47×，TTFT 反而变差。
  T4 的 INT8 Tensor Core 峰值是 fp16 的 2 倍，是唯一能把算力受限区和 prefill 也抬起来的路线。
- 依据：v0.28.0 源码目录 `csrc/libtorch_stable/quantization/w8a8/cutlass/` 里有 `scaled_mm_c2x_sm75_dispatch.cuh`（我打开过）。
- 零成本先跑现成权重：

```bash
vllm serve RedHatAI/Qwen2.5-1.5B-Instruct-quantized.w8a8 --dtype half --max-model-len 4096
# 对照臂：RedHatAI/Qwen2.5-1.5B-Instruct-quantized.w8a16（只省访存）、Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int8
# 日志应出现 CutlassInt8ScaledMMLinearKernel
```

- 再自己量化（补「量化过程不是我做的」这条）：`pip install llmcompressor`，模型显式 `torch_dtype=torch.float16`（Qwen2.5 config 是 bf16，T4 无 bf16），
  recipe `SmoothQuantModifier(smoothing_strength=0.8)` + `GPTQModifier(targets="Linear", scheme="W8A8", ignore=["lm_head"])`，
  `oneshot(dataset="HuggingFaceH4/ultrachat_200k", num_calibration_samples=512)`。先 0.5B。
- 跑前预测：并发 1 W8A8 加速 1.3–1.5×（低于 INT4 的 1.9×）；并发 16–32 吞吐 ≥1.6× fp16 且高于 INT4 的 1.47×；并发 ≥8 时 TTFT 降 ≥20%。
  若并发 32 下 W8A8 仍不如 INT4，说明瓶颈已不在 GEMM，预测被推翻。

### C. lm-eval 真实精度

```bash
pip install lm_eval
for M in Qwen/Qwen2.5-1.5B-Instruct Qwen/Qwen2.5-1.5B-Instruct-AWQ Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4; do
  lm_eval --model vllm --model_args pretrained=$M,dtype=float16,gpu_memory_utilization=0.85,max_model_len=4096,add_bos_token=true --tasks wikitext --batch_size auto
  lm_eval --model vllm --model_args pretrained=$M,dtype=float16,gpu_memory_utilization=0.85,max_model_len=4096 --tasks gsm8k --num_fewshot 5 --limit 1000 --batch_size auto
  lm_eval --model vllm --model_args pretrained=$M,dtype=float16,gpu_memory_utilization=0.85,max_model_len=4096 --tasks mmlu_stem --num_fewshot 5 --batch_size auto
done
```

- 坑：lm-eval 的 vllm 后端 dtype 只接受 `float16 / bfloat16 / float32 / auto`，写 `half` 会报错，`auto` 会按 config 走 bf16。
- gsm8k 的参数与 vLLM 自己的量化 CI（`.buildkite/lm-eval-harness`）一致，可直接对照它的参考值。
- 跑前预测：AWQ 相对 fp16 PPL 上升 ≤5%，GPTQ-Int4 5–12%；gsm8k AWQ 掉 ≤3 分、GPTQ 掉 3–6 分。若 GPTQ 的 PPL 反而低于 AWQ 则推翻。

### D. n-gram 投机解码

- 为什么：roofline 已证明 batch=1 解码由权重读取主导，算力闲着。n-gram 不需要 draft 模型、不占显存，
  用 1+k 个 token 的验证换多个 token；把已有并发曲线和拐点串起来：每步验证 token 数 B×(k+1) 越过拐点就翻转。

```bash
vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype float16 --max-model-len 4096 \
  --speculative-config '{"method":"ngram","num_speculative_tokens":5,"prompt_lookup_max":4,"prompt_lookup_min":2}' \
  --per-request-spec-decode-metrics summary
```

- 负载分四类：摘要、RAG 抽取式问答、代码改写（n-gram 最强）、无上下文闲聊（阴性对照）。指标：响应体 `metrics.speculative_decoding.mean_acceptance_length`。
- 跑前预测：摘要/RAG 的 batch=1 TPOT 加速 ≥2.0×，闲聊 0.95–1.10×；k=5 时 B=8 吞吐低于基线 ≥20%，k=2 的翻转在 B=8–16。
  反例警告：vLLM issue #16258 在 L4 上小模型开 ngram 吞吐反降 2×，固定开销可能吃掉收益。

### E. 内核消融

```bash
vllm serve Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4 --dtype half --linear-backend marlin   # / exllama / triton
```

- `--linear-backend` 是 v0.28.0 的正式旗标（`vllm/config/kernel.py::LinearBackend`，我打开过，含 marlin / exllama / triton）。
- 为什么：roofline 里「量化只吃到理论收益 75%，残差指向反量化」是从残差反推的。换内核就是不做 ncu 的因果验证。
  PR #29901 自己说 Turing 上 Marlin 在 m>8 时慢于 Exllama 的「反量化 + cuBLAS」路径，所以并发越高 Exllama 越可能反超。
- 跑前预测：并发 1–4 Marlin 的 TPOT 比 Exllama 低 ≥15%；并发 ≥16 Exllama 反超 ≥10%；三内核 wikitext PPL 差 <0.05。

### F. 前缀外推 8k + 45% 惩罚复现

- vLLM：`vllm bench serve --dataset-name prefix_repetition --prefix-repetition-prefix-len {2048|4096|8192} --prefix-repetition-suffix-len 128 --prefix-repetition-num-prefixes {4|200}`。
- SGLang：`python -m sglang.bench_serving --dataset-name generated-shared-prefix --gsp-system-prompt-len {2048|4096|8192} --gsp-num-groups {4|200} --flush-cache`。
- 两框架 chunk 预算都钉 16384，四象限：缓存开/关 × 全共享/全不同。
- 「SGLang 无复用时 RadixAttention 让 TTFT 恶化 45%」与 LMSYS 原博客「no noticeable overhead even in the absence of cache hits」矛盾，
  官方 issue 里没有对应记录。四象限先分离 radix 树开销与 Colab 2 vCPU 的 tokenizer 争抢，再提 issue。
- 跑前预测：8k 前缀命中时两框架 TTFT 降幅 ≥85%；SGLang 惩罚绝对值 ≥100 ms 且不随前缀变长而消失；vLLM 惩罚全程 <10%。

### G. 官方压测工具交叉复测

- 用 `vllm bench serve --backend openai-chat` 打 SGLang，用 `sglang.bench_serving --backend vllm` 打 vLLM，并发 1/8/32 三点复测。
- 再把闭环并发改为开环：`--request-rate {1,2,4,8} --burstiness 1.0 --goodput ttft:500 tpot:50`。
- 跑前预测：两官方工具与自写脚本吞吐差 <10%，TTFT p99 差可 >20%；rate=8 时 goodput <50%，rate=2 时 >90%。

### H. 评测最小组合（约 6 h GPU）

| 项 | 工具 | 备注 |
