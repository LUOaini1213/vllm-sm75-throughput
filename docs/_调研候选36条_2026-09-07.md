##  1. [spec_decode] P1 · hours · sm75=confirmed · spec-ngram-batch-crossover
**n-gram 投机在并发增大时的翻转点：验证 B×(k+1) 是否落在你测出的 8~16 拐点**

- **what**: 在候选 1 的最优配置上做并发扫描 B∈{1,2,4,8,16} × k∈{2,5}，找到投机吞吐低于基线的翻转并发，并检验翻转点是否由'每步验证的总 token 数 B×(k+1) 越过算力拐点'决定，而不是由 B 单独决定。
- **why_now**: 这是把你已完成的并发曲线（实验 1）和 roofline 拐点（实验 4）直接串起来的实验：投机解码把每步 token 数从 B 放大到 B×(k+1)，理论上会把你测出的带宽→算力拐点提前 (k+1) 倍。vLLM 博客与 arXiv 2601.11580 都报告高负载下投机变慢（最高 1.8× slowdown），但都是 H100 上的数据，T4 拐点低得多，翻转会发生在很小的并发上，这个数字很有面试价值。
- **how**: 服务端同候选 1，加 --max-num-seqs 32；客户端并发 B∈{1,2,4,8,16}，用摘要负载（高接受率）+ 闲聊负载各跑一遍；k∈{2,5}，prompt_lookup_max 取候选 1 最优。
记录：总吞吐 tok/s、每请求 TPOT、/metrics 里 draft/accepted 计数（接受率随 B 基本不变，可用于分离'接受率'与'验证成本'两个因素）。
对照分析：把每步验证 token 数 M=B×(k+1) 作为横轴，把投机的单步耗时与你实验 1 中并发=M 的基线单步耗时画在同一张图上，看是否重合。
注意：vLLM 的 num_speculative_tokens_per_batch_size（按并发动态选 k、可设 0 关闭）文档只列 eagle/eagle3/dflash，对 ngram 不适用，所以这里用'每个 B 单独指定 k'来模拟自适应策略。

- **prediction**: 写死：(1) 摘要负载下，k=5 的投机吞吐在 B=4 时与基线之差在 ±10% 内，B=8 时低于基线 ≥20%；k=2 的翻转出现在 B=8~16 之间。(2) 投机单步耗时与基线并发=B×(k+1) 的单步耗时在 M≤32 范围内误差 ≤15%（即翻转点由 M 决定）。可推翻点：若 k=2 与 k=5 在同一个 B 翻转，或投机单步耗时明显高于基线在 M 处的耗时，说明额外开销来自拒绝采样/CPU 提案而非 GEMM 算力，roofline 解释被推翻。

##  4. [quant_more] P1 · hours · sm75=confirmed · linear-backend-kernel-ablation-t4
**T4 上 Marlin(sm75) vs Exllama vs Triton 内核消融：先修正'T4 无 Marlin'这个前提**

- **what**: vLLM 0.28.0 已通过 PR #29901（2025-12 合入）给 Turing 加了 Marlin：无 cp.async 改同步 load、m16n8k8 双发模拟 m16n8k16、Turing 上改用 FP16 累加器。源码里 MarlinLinearKernel.get_min_capability()=75，且在 CUDA 候选表中排在 Exllama 之前 —— 所以你之前 T4 上 AWQ/GPTQ-Int4 的 1.9×/1.47× 大概率已经是 Marlin-sm75 数字。用 0.28.0 新增的 `--linear-backend marlin|exllama|triton` 在同一 checkpoint 上做并发扫描 + 精度一致性，把'反量化开销'从 roofline 残差里拆出来。
- **why_now**: 你 roofline 里'量化只吃到理论访存收益 75%，残差指向反量化开销（未做 ncu）'这条，不用 ncu 也能用内核切换做因果验证。Exllama 路径在 M>50 时改走 反量化+cuBLAS hgemm（q_gemm.cu `MAX_Q_GEMM_ROWS 50`），PR #29901 明说 Turing 上 Marlin 在 m>8 时慢于这条路径 → 你观察到的'并发 8~16 拐点'可能部分是内核特性而非纯带宽/算力切换。另外 Marlin-sm75 用 FP16 累加，精度是否变差可以顺手回答。
- **how**: 1) 先确认现状：启动 `vllm serve Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4 --dtype half`，看日志中 auto_gptq 打印的 kernel backend（`_kernel_backends_being_used`），预期是 MarlinLinearKernel。2) 三组：`--linear-backend marlin` / `--linear-backend exllama` / `--linear-backend triton`（值定义在 vllm/config/kernel.py 的 LinearBackend；CLI 在 arg_utils.py `--linear-backend`；设了非 auto 后只在该后端集合里选，选不到直接报错）。AWQ 同样三组（AWQ zero_point=true → uint4 带零点，Marlin 支持；Exllama 要求 fp16 激活，T4 正好）。3) 并发 1/2/4/8/16/32 记 TPOT/TTFT/吞吐。4) 精度：同一 checkpoint 三内核各跑一次 wikitext PPL（见 lm-eval 候选）或你现有的与 fp16 贪心一致率。5) 可加 `--enforce-eager` 交叉，排除 CUDA graph 捕获差异。
- **expected_effect**: PR #29901 在 2080Ti 上的数据：n=1024,k=2048,m=1024 时 fp16 0.0900ms、Marlin W4A16 0.0778ms、Marlin W4A8-INT8 0.0547ms；PR 明确 Marlin 在小 batch 占优、m>8 时慢于 Exllama(反量化+cuBLAS)。因此预期并发越高 Exllama 越占优，出现交叉点。这条实验的产出是'T4 上 INT4 内核选择的交叉点'和'FP16 累加是否伤精度'两个可写进简历的结论。
- **prediction**: 并发 1~4：Marlin TPOT 比 Exllama 低 ≥15%；并发 ≥16：Exllama 反超 ≥10%；TritonW4A16 在所有并发都最慢。精度：三内核 wikitext PPL 差 <0.05；若 Marlin 明显更差（>0.1），归因于 Turing 上的 FP16 累加。若 Exllama 在任何并发都不反超，则 PR 里 2080Ti 的结论不适用于 T4（推翻）。

##  8. [serving_knobs] P1 · hours · sm75=confirmed · chunk-budget-ttft-tpot-frontier-both
**两框架 prefill 分块预算扫描：vLLM --max-num-batched-tokens / --long-prefill-token-threshold 对 SGLang --chunked-prefill-size / --enable-mixed-chunk，画 T4 上 TTFT–TPOT 取舍前沿**

- **what**: 固定并发 16 与混合长度输入（1k±80%），vLLM 扫 --max-num-batched-tokens ∈ {512,1024,2048,4096,8192,16384}，再在 16384 档加 --long-prefill-token-threshold ∈ {256,512}；SGLang 同口径扫 --chunked-prefill-size ∈ {-1,512,2048,8192,16384}，每档 ± --enable-mixed-chunk。输出 TTFT p50/p99、TPOT p50/p99、输出吞吐三张曲线，把两框架按相同 token 预算叠在一张图上。
- **why_now**: 已有并发曲线全是默认预算下测的，而 vLLM 0.28 把默认 max_num_batched_tokens 从 8192 提到 16384（PR #51726，2026-08-11 合并；回滚 PR #51908 未合并），意味着 T4 上 ≤16k 的 prefill 一步做完、所有在跑 decode 被整段阻塞——这能直接解释你并发曲线里 TPOT 的形状；SGLang 在 T4 上的 chunked-prefill-size 是按显存自动设的（文档只写 'Automatically set based on GPU memory'，源码 _handle_gpu_memory_settings 未能打开，要从启动日志读），你已有的 SGLang 数据是在未知 chunk 值下测的。vLLM 官方文档给出的取舍口径是：小值（2048）优化 ITL、大值优化 TTFT；源码里 long_prefill_token_threshold 会把长请求每步 token 数截到阈值（scheduler.py 两处 `if 0 < threshold < num_new_tokens`），是不改预算就压 TPOT 尖峰的独立旋钮。JD 的 'SGLang/vLLM 优化' 直接对应。
- **how**: vLLM：`vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype half --max-model-len 8192 --gpu-memory-utilization 0.9 --max-num-seqs 32 --max-num-batched-tokens {512|1024|2048|4096|8192|16384} [--long-prefill-token-threshold 256]`；客户端 `vllm bench serve --backend vllm --model Qwen/Qwen2.5-1.5B-Instruct --dataset-name random --random-input-len 1024 --random-output-len 128 --random-range-ratio 0.8 --num-prompts 200 --max-concurrency 16 --ignore-eos --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 --save-result --seed 1`（每档重启服务器，文档警告对同一服务器重复跑会因残留前缀缓存虚高吞吐）。SGLang：`python -m sglang.launch_server --model-path Qwen/Qwen2.5-1.5B-Instruct --dtype half --attention-backend triton --sampling-backend pytorch --mem-fraction-static 0.80 --max-running-requests 32 --chunked-prefill-size {-1|512|2048|8192|16384} [--enable-mixed-chunk]`；客户端 `python -m sglang.bench_serving --backend sglang --dataset-name random --random-input-len 1024 --random-output-len 128 --random-range-ratio 0.8 --num-prompts 200 --max-concurrency 16 --output-file chunk_{n}.jsonl`。先在启动日志里记录 SGLang 自动选出的 chunked_prefill_size / cuda_graph_max_bs 作为基线。注意 --enable-mixed-chunk 那一步整批走 prefill kernel（sglang issue #2273 搜索摘要，未逐字打开），不走 CUDA graph。
- **expected_effect**: 依据文档取舍口径与源码：预算越小 TPOT p99 越低、吞吐越低；long-prefill-threshold 只截长请求，短请求 TTFT 不受影响。量级估计（1.5B fp16，T4 prefill 约几千 tok/s）：一次 4k prefill 约 0.7–1.5 s，budget=16384 时并发 decode 的 TPOT p99 会被拉到秒级；budget=1024 时该 prefill 被分成 4 步，TPOT p99 回到 ~200–400 ms 量级。
- **prediction**: 并发 16 下，vLLM 预算从 16384 降到 1024 时 TPOT p99 至少降 3×，输出吞吐降幅 <15%；512 档吞吐降幅 >20%。在 16384 档加 --long-prefill-token-threshold 256，TPOT p99 能回到与 2048 档 ±20% 以内，且短请求 TTFT p50 变化 <5%。SGLang 开 --enable-mixed-chunk 后 TPOT p99 降 ≥30%，但 TPOT p50 上升 10–30%（mixed 步丢 CUDA graph 走 eager prefill kernel）；同预算下 SGLang 比 vLLM 在小 chunk 时吞吐掉得更多。

- **what**: 把已有 2380 字符前缀实验的前缀长度扫到 {2k,4k,8k,12k} tokens（后缀 128、输出 128），两框架各跑'缓存开/关'×'全部共享/全部不同'四象限，报告 TTFT、吞吐、以及'无复用惩罚'（缓存开但零命中 vs 缓存关）随前缀长度的变化曲线。

## 35. [quant_more] P4 · hours · sm75=likely · bnb-nf4-plugin-and-hqq-calibration-free-baselines
**免校准 4bit 基线：bitsandbytes NF4（vLLM 0.28.0 需装 vllm-bnb-plugin）与 HQQ，对比 GPTQ/AWQ 的精度与速度代价**

- **what**: vLLM 0.28.0 已把 bitsandbytes 移出主仓（PR #43529），需 `pip install vllm-bnb-plugin`（插件 get_min_capability=70，支持 in-flight 4bit 与预量化 4/8bit checkpoint）。用它对 fp16 权重做 in-flight NF4，与 Marlin GPTQ/AWQ 比 TPOT 和 PPL；HQQ 只在 HF transformers 里做 PPL 对照（0.28.0 的 QUANTIZATION_METHODS 已无 hqq）。
- **why_now**: 补齐'量化方法谱系'的免校准一端；bnb 在 vLLM 里是公认慢路径（issue #9535：A100 上 4bit 反比 fp16 慢 ~58%，最后 stale 关闭），T4 上量化一下'慢多少、精度差多少'是低成本数据点，也顺带验证插件在 0.28.0+T4 是否能用。
- **how**: `pip install vllm-bnb-plugin "bitsandbytes>=0.48.1"`（插件通过 vllm.general_plugins 入口自动注册）；`vllm serve Qwen/Qwen2.5-1.5B-Instruct --quantization bitsandbytes --load-format bitsandbytes --dtype half`，并发 1/8/32；HQQ：`from transformers import HqqConfig; HqqConfig(nbits=4, group_size=128)` 加载后用 `lm_eval --model hf` 跑 wikitext（HQQ 免校准、几分钟内完成）。
- **expected_effect**: bnb NF4 bs=1 TPOT 预计与 fp16 持平或更慢（反量化后走 fp16 GEMM，无融合内核），比 Marlin 慢 ≥2×；PPL 与 AWQ 接近（小模型 NF4 g64 ΔPPL 0.3~0.6）；HQQ 4bit g128 PPL 略高于 GPTQ。
- **prediction**: bnb NF4 在 T4 上 bs=1 TPOT ≥ fp16 的 0.9×（即不加速）；HQQ PPL 比 GPTQ 高 0.1~0.4。若 bnb 反而比 fp16 快 >1.3×，则插件已带融合内核（推翻）；若插件在 0.28.0 wheel 上 import 失败，记录为版本不兼容。

7) GPTQModel 6.1.0（2026-04）：CUDA 内核改为 JIT 编译，Marlin 支持 Turing+；AWQ 的 zero_point 参数并入 sym；desc_act=False 时默认 act_group_aware。AutoRound 时序表（A100）：Qwen2.5-0.5B W4G128 默认 recipe 2 分钟、best 7 分钟。
8) SGLang：官方曾计划在 0.5 弃用 sm75（issue #7467 引 #6006）；Triton ≥3.3 在 cc<80 的 tl.dot 有过 'Unsupported conversion from f16 to f16' 回归，降 Triton 3.2 可绕过——你 torch 2.13 环境下若 Triton W4A16 或 SGLang triton 后端出现该错误，这是原因。sgl-kernel PyPI cu12x 轮子不含 sm75 cubin（CMake 只有 80/86/89/90/100/120；issue #5062 说只有 cu118 轮含 sm75）。
9) 现成对照 checkpoint（全部 Qwen2.5-1.5B-Instruct 同族，免自己量化即可做 fp16/W8A16/W8A8/GPTQ-Int4/AWQ 五臂对比）：RedHatAI/Qwen2.5-1.5B-Instruct-quantized.w8a8、RedHatAI/Qwen2.5-1.5B-Instruct-quantized.w8a16、Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int8（bits=8,g128,sym,desc_act=false）、官方 GPTQ-Int4（g128,sym,desc_act=false）、官方 AWQ（g128, zero_point=true）。RedHatAI 0.5B w8a8 的 recipe.yaml 是纯 GPTQ(W8A8, observer mse, damp 0.01) 不含 SmoothQuant。
10) 未查到的（标 unknown，勿写成事实）：T4 上 llm-compressor/GPTQModel 对 0.5B/1.5B 的实际耗时；lm-eval 各任务在 T4 的耗时；vllm-bnb-plugin 与 0.28.0 wheel/T4 的兼容性；HQQ README 声称 'You can use HQQ in vllm' 的具体机制在 0.28.0 下是否仍成立。
