SGLang 并发 16 凹陷 —— 根因定位
Colab Tesla T4 · SGLang 0.5.19 · Qwen2.5-0.5B-Instruct · 跑于 2026-09-05
--context-length 2048 --mem-fraction-static 0.80 --attention-backend triton --sampling-backend pytorch

================================================================
结论（先说）
================================================================
**根因：解码 CUDA graph 只捕获到 batch size 8。**

SGLang 启动日志原文：
  Capture target decode CUDA graph begin. backend=full, num_tokens_per_req=1,
  bs=[1, 2, 4, 8], avail mem=1.91 GB

batch > 8 时没有对应的图可用，回落 eager 执行，**每 token 解码延迟一步跳约 4.8 倍**：

  batch    8 → TPOT p50  6.23 ms   （有图）
  batch   10 → TPOT p50 29.76 ms   （无图，eager）
  batch   12 → 29.76 ms
  batch   14 → 28.51 ms
  batch   16 → 31.01 ms
  batch   18 → 31.52 ms
  batch   32 → 31.74 ms

台阶在 **8 → 10 之间**，之后一路持平。

**为什么表现为「并发 16 凹陷」**：吞吐 ≈ batch / TPOT。
  并发  8：8 / 6.65ms  ≈ 1200 tok/s   （实测 1027.5）
  并发 16：16 / 31.35ms ≈  510 tok/s   （实测  488.5）
  并发 32：32 / 32.49ms ≈  985 tok/s   （实测  950.9）
从 8 到 16，batch 翻倍但 TPOT 涨了 4.7 倍 → 吞吐掉一半；
从 16 到 32，batch 再翻倍而 TPOT 不变 → 吞吐回升。
**「凹陷」是这条台阶与 batch 翻倍两者相除的产物，不是 16 这个数字本身有问题。**

捕获范围被显存卡死：`avail mem=1.91 GB`（0.5B 模型 + mem-fraction-static 0.80 之后的余量）。

四个实验的判定（判据均在跑之前写死）
================================================================
【实验 0 · 并发细扫 8/10/12/14/16/18/20/24/32】
  吞吐 326.0 / 313.8 / 386.5 / 453.9 / 495.1 / 404.0 / 633.2 / 701.9 / 945.1
  按「相对基准 < 0.6 算塌陷」的判据：**塌陷档位：无 → 本轮没复现凹陷**。
  判据里写了这种情况要「先解释矛盾再往下」——解释就是上面那条：
  凹陷取决于**扫描列表里相邻两档的 batch 倍数**，不是某个并发值。
  细扫里相邻档只差 2（8→10→12…），batch 倍数小，吞吐就没有回落形态。
  **这一条直接推翻了上一轮「并发 16 是真实凹陷」的表述** —— 现象可复现，
  但把它归因到「并发 16」是错的，应归因到「batch>8 掉出 CUDA graph」。

【实验 1 · 调度器日志切片】→ **排除调度/排队层**
  并发 8：#running-req 0/8/8，#queue-req 0/0/0，preempt 0 次
  并发 16：#running-req 0/16/16，#queue-req 0/0/0，preempt 0 次
  没有排队、没有抢占，running-req 恰等于请求并发。瓶颈不在调度。

【实验 2 · 扫 --chunked-prefill-size 512 / 2048 / 8192】→ **排除 chunked prefill**
  cps      并发8     并发16    并发32    16/8
  512     1023.0    465.8     967.4     0.46
  2048    1027.5    488.5     950.9     0.48
  8192     875.1    503.2     975.4     0.58
  16/8 比值 0.46~0.58，**凹陷纹丝不动**，与该参数无关。

【实验 3 · 默认 flashinfer 后端】→ **未完成**
  服务在 420s 内没起来，会话结束前没拿到数据。**不能说"默认后端也有凹陷"，
  也不能说"没有"** —— 这一条仍是未测。

可验证的下一步（本轮未做）
================================================================
若根因是 CUDA graph 捕获上限，那么 **提高 `--cuda-graph-max-bs` 应当让台阶右移**。
这是一个能直接证伪的预测：
  - 台阶跟着参数移动 → 根因坐实
  - 台阶不动 → 上面的解释站不住，要重查
受限于显存（avail mem 1.91 GB），可能需要同时下调 `--mem-fraction-static` 腾空间。
**本轮没跑这一步，结论目前建立在「日志写明 bs=[1,2,4,8]」+「TPOT 台阶恰在 8 之后」
这两条证据的吻合上，属强关联，不是因果实证。**

边界
================================================================
1. 单实例、单卡 T4、0.5B、2048 上下文、Triton+PyTorch 后端。
2. 实验 0 每档单次；但台阶特征在实验 2 的三组 cps 里重复出现，可信度较高。
3. **CUDA graph 是强关联证据，不是对照实验**。要坐实须扫 --cuda-graph-max-bs。
