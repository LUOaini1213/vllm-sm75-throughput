量化对照：fp16 vs AWQ vs GPTQ-Int4
Colab Tesla T4 (sm_75, 15360 MiB, 无 Marlin) · Qwen2.5-1.5B-Instruct
vLLM 0.28.0 · max-model-len 2048 · gpu-memory-utilization 0.85 · 跑于 2026-09-05

对应 JD：「开展模型量化实验（INT4 QAT / GPTQ / AWQ），验证精度与性能平衡」
做的是训练后量化（PTQ），加载社区已量化权重。**QAT 未做。**

================================================================
一、跑之前写下的预测 —— 【已被数据推翻】
================================================================
原文（notebook 第 0 节，跑之前写的）：

  「T4 是 sm_75。vLLM 的 GPTQ 快速路径 Marlin kernel 要 sm_80 以上，在 T4 上会回落到
    老的 GPTQ kernel。所以有理由预测：在 T4 上，GPTQ-Int4 的吞吐可能不如 fp16。」

**结果：预测错了，而且错得很彻底。** GPTQ-Int4 不但没有慢于 fp16，
反而在低并发快约 1.9 倍，全并发区间都稳定领先，与 AWQ 基本持平。

「T4 无 Marlin」这个前提是对的（notebook 第 0 节实测打印确认 compute capability 7.5）。
错的是推论：我默认了「kernel 效率」是瓶颈，但没有验证这个前提。

不改预测去迎合数据 —— 原文照留在上面。

================================================================
二、吞吐（tok/s）
================================================================
 并发    fp16      AWQ    GPTQ-Int4    AWQ/fp16   GPTQ/fp16
    1    66.3    124.9      126.2        1.88×      1.90×
    2   125.1    241.6      254.7        1.93×      2.04×
    4   248.5    444.3      490.1        1.79×      1.97×
    8   419.6    787.2      761.2        1.88×      1.81×
   16   780.6   1251.9     1337.2        1.60×      1.71×
   32  1163.3   1703.9     1706.8        1.46×      1.47×

—— 两种 PTQ 在**全并发区间**都快于 fp16；优势随并发升高而收窄（1.9× → 1.47×）。
—— AWQ 与 GPTQ 互有胜负，差距在测量噪声量级，**不宜宣称谁更快**。

================================================================
三、延迟与显存
================================================================
                    fp16      AWQ    GPTQ-Int4
  TPOT p50 @并发1  14.89ms   7.79ms    7.70ms
  TTFT p50 @并发8   55.2ms   65.4ms    68.8ms
  KV cache tokens  337,536  381,648   381,056
  服务就绪耗时         76s     124s      134s

—— **TPOT 几乎腰斩**（14.89 → 7.7~7.8 ms），这是吞吐领先的直接来源。
—— **但 TTFT 反而略差**（55.2 → 65~69 ms）：量化省的是权重读取，
   prefill 阶段的计算量没变，反量化还要额外开销。
   **省显存 + 快解码，代价是首 token 稍慢** —— 这个取舍值得单独讲。
—— 权重变小让 KV cache 多出约 4.4 万 tokens（+13%）。
—— 量化版启动更慢（124/134s vs 76s），是反量化与 kernel 准备的一次性成本。

关于为什么预测错了（**这是假说，本轮没有测量证据，不要当结论讲**）：
  1.5B 模型在 T4 上解码阶段大概率是**权重读取带宽受限**，INT4 权重约为 fp16 的 1/4，
  省下的访存量压过了 kernel 效率的损失。TPOT 几乎减半与这个方向一致，
  但我没有做带宽剖析来证实。要坐实得跑 roofline 或 nsight 剖析，本轮没做。

================================================================
四、精度代理：与 fp16 的贪心输出一致率
================================================================
16 个固定技术类提示，temperature=0，max_tokens=96，三个变体同一套提示。

              完全一致   字符相似度均值   首次分叉字符位（中位）
  AWQ          0/16        0.191            23
  GPTQ-Int4    0/16        0.220            22

**这个数字非常容易被误读，务必连同下面三条一起说：**

1. **输出全部正常。** 长度中位数 fp16/AWQ/GPTQ = 508/527/516 字符，无空串，
   三份回答都连贯、切题、事实上没问题。低一致率不是采集故障。
2. **贪心全文一致率是一个过于严苛的代理。** 早期只要有一个 token 不同，
   后面就整段发散；首次分叉中位在第 22–23 个字符，正是这个机制。
   它衡量的是「能否复现 fp16 的逐 token 输出流」，
   **不是「量化版更差」**。
3. **没有做任务准确率。** PPL 未取得：transformers 加载 GPTQ 需要 `optimum`、
   AWQ 需要额外后端，本轮不愿再引入依赖链（SGLang 那轮已在依赖上耗掉很久）。
   要谈任务能力得另跑 LongBench 之类的基准，**本轮没跑**。

================================================================
五、边界
================================================================
1. **量化过程不是我做的** —— 用的是 Qwen 官方已量化权重
   （Qwen2.5-1.5B-Instruct-AWQ / -GPTQ-Int4）。
   简历只能写「做了 PTQ 变体的性能与精度对照」，
   **不得写「实现了量化算法」**。
2. **QAT 完全没做。** 面试如实说「PTQ 做了两种，QAT 只懂原理没做过」。
3. 单次测量、无重复跑、无置信区间。
4. 单卡 T4 / 1.5B / 2048 上下文，不可外推到大模型、长上下文或多卡。
5. 途中修掉一个**自己写的** bug：启动器里 `r"Maximum concurrency[^\n]*"` 没有捕获组，
   `m.group(1)` 抛 IndexError 被外层 `except Exception: pass` 吞掉，
   导致就绪后仍无限重试到超时。已加捕获组并把 except 收窄成只吞连接失败，
   同类检查已写进 `_check_nb.py`。
