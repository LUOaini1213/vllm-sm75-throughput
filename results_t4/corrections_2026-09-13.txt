零、先补一条 09-08 那份文件漏写的口径
================================================================
压测脚本是 notebook cell 8 现写出来的 probe.py：

  --max-tokens 默认 128            每个请求输出 128 个 token
  n_req = max(4 * 并发, 16)        并发 >= 4 时即 4 × 并发

也就是每个并发槽顺序跑满 4 轮。所以墙钟的自洽式是

  墙钟 ~= (请求数 / 并发) x (TTFT + 127 x TPOT) = 4 x (TTFT + 127 x TPOT)

不是「TTFT + 511 x TPOT」—— 后者把 4 轮当成 1 个 512 token 的请求，会把 C 组整组
推到 +8~14%，正好把真正的离群格掩盖掉。

口径的直接验证（不依赖上式）：墙钟 x 吞吐 / 请求数 = 每请求输出 token 数。
23 个格子全部落在 127.78 ~ 128.16 之间，与 max_tokens=128 吻合。

二、三条不需要任何反推、直接看表就能看出的矛盾
================================================================
上面那一步用了模型（自洽式）。下面三条只用同一张表里的数互相比，不用任何模型：

  1. 同一组内不单调：A 组 batch 24 吞吐 670.0，batch 32 反而掉到 608.0；
     而 TPOT 只从 32.80 涨到 35.74 ms（+9%）。batch 涨 33%、每 token 只慢 9%，
     吞吐没有理由下降。

  2. 与劣化组比反了：吞吐口径下 B32 / A32 = 856.6 / 608.0 = 1.41x。
     但同一份文件第二节的 B / A 表（TPOT 口径）在 batch 32 处是 1.02x。
     B 是「把解码 CUDA graph 整个关掉」的劣化组，在 batch 12/16/24 上
     A / B 的吞吐是 0.945 / 0.955 / 0.972（A 略慢，因为两组此时都无图可用），
     不可能到了 batch 32 就变成 B 比 A 快 41%。

  3. 与默认后端比反了：D 组（默认后端，同样只捕获到 bs=[1,2,4,8]，batch 32 无图可用）
     实测 945.6 tok/s，同样远高于 A 的 608.0。

三条各自独立，指向同一个结论：608.0 这一格的墙钟里有一段与解码无关的开销。

四、这段 7.8 秒是什么，本文件不下结论
================================================================
能说的只有：它不在解码里（TPOT 35.74 ms 与同组 batch 12/16/24 的 32.8~35.0 同量级），
也不在首 token 里（TTFT 241.5 ms，四轮合计不到 1 s）。

09-08 文件第六节第 3 条把它与 sglang_outliers_repeat_2026-09-05.txt 里
「并发 4 间歇不稳定（极差比 3.17x）」记为同一现象。batch 32 这一格属于第三次出现。

要定性只有一条路：重跑 A 组 batch 32（单参数、单次，Colab T4 十几分钟），
看 26.92 s 复现不复现。本轮没跑，所以这里只更正数字，不给原因。
